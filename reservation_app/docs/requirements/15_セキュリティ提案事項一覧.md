# 15. 🔒 セキュリティ提案事項一覧

> Claude Codeで clinic-app（診療予約・患者情報管理・電子カルテ）専用のセキュリティ用スキル・エージェントを作成した際に検討した提案事項を、要件定義書とは別にリストアップしたもの。実装・レビューの際のToDoとして使う想定。

## 1. 背景

- 目的は2点: **外部へのデータ流出を避ける**こと、**流出が起きた場合でも被害を最小限に収める構成にする**こと。
- 現状の実装は anon key を使う単一の Supabaseクライアント（`lib/supabase.ts`）。anon keyはブラウザに公開される前提の鍵のため、**RLS（Row Level Security）だけが実質的なアクセス制御**になる。
- 職員認証は現状パスコード `staff` の共有ログインのみ（[非機能要件](12_非機能要件.md)にも「本番非対応のプロトタイプ」と明記済み）。

## 2. 外部への流出を防ぐための提案

- [ ] 患者PII・経過記録テーブルにRLSを設定し、デフォルト拒否+認証済み職員限定のポリシーを明示する（未設定 = 全世界に公開と同義）
- [ ] 患者PII・経過記録への問い合わせをanon keyクライアントから直接行わず、Server Component / Route Handler / Server Action経由にする
- [ ] service role keyなど秘密情報を`NEXT_PUBLIC_*`に入れない。専用のサーバー限定クライアント（例: `lib/supabase-server.ts`）を分離する
- [ ] `.env*`がコミットされていないか、鍵・パスワードを含むファイルが混入していないか定期的に確認する
- [ ] 患者検索・予約APIにレート制限と認可チェックを入れ、総当たりで他人のPIIを引けないようにする（enumeration対策）
- [ ] console.log・エラートラッキング・アクセスログにPII（実名・住所・保険証番号・SOAP本文）を出力しない
- [ ] 外部SaaS（アナリティクス・エラートラッキング・通知サービス等）を追加する際、PIIが送信先に渡らない設定になっているか確認する
- [ ] 使わないAPIエンドポイント・CORSの公開範囲を必要最小限にする
- [ ] 診断書・紹介状・検査サマリー等の生成にAIを利用する場合、患者PII・診療情報を外部の一般公開AI API/SaaSに送信しない（閉域環境でホストするモデルを利用し、送信先を限定する）

## 3. 漏洩時の被害を最小化するための提案（blast radius reduction）

- [ ] 患者PII・保険証番号などを保存時暗号化し、暗号鍵をデータ本体と分離管理する
- [ ] 受診完了から2ヶ月でPIIを自動パージするジョブを実装し、失敗時に検知・通知できるようにする
- [ ] 共有パスコード運用から個別アカウント・多要素認証・一定時間無操作での自動ログアウト・退職者アカウントの即時停止へ移行する
- [ ] 将来の職種別権限（医師/看護師/その他職員/管理者）拡張を見据え、今のうちに最小権限で権限をコードに表現しやすい設計にしておく
- [ ] ヘッダー編集・SOAP記録に改ざん検知可能な監査証跡（誰が・いつ・何を変更したか、訂正履歴として保持）を残す
- [ ] バックアップを暗号化し、本番環境と分離した場所に保管、変更・削除から保護し、定期的に復元テストする
- [ ] 診療予約・電子カルテ・福祉タクシー予約のデータを分離し、システムを跨いだ不要な結合・共通化をしない
- [ ] 鍵流出・不正アクセスが疑われた際に鍵のローテーション/アカウント無効化を即座に行える手順をあらかじめ用意する

## 4. 実装フローの提案

- [ ] Supabaseテーブル/ポリシー、認証、患者検索、環境変数、ログ出力に関わる変更をしたら、上記チェックリストと突き合わせる
- [ ] 変更後は専用の`clinic-security-reviewer`エージェント（Claude Code, `clinic-app/.claude/agents/`配下）でレビューする
- [ ] 要件定義書の非機能要件と食い違う実装をする場合は、要件定義書側の更新も合わせて提案する

## 5. 追加で検討すべき提案（元メッセージの3点目が未記入だったため、一般的な観点から補足）

- [ ] 第三者（外部委託先・ベンダー）にデータを渡す場合の委託先管理・契約上のセキュリティ要件
- [ ] 監査ログ自体の保存期間・アクセス制限（誰が監査ログを見られるか）
- [ ] 万一の漏洩時に、どこに・いつまでに報告するか（個人情報保護委員会への報告義務、患者への通知）というインシデント対応・通知プロセス
- [ ] 開発環境・テスト環境に本物の患者データ（実データ）を使わない運用ルール

## 6. 既知の既存ギャップ（参考・現状把握）

- 職員認証が共有パスコードのみ（個別アカウント化・MFAが未実装）
- RLSポリシーの設定状況が未確認
- PII自動パージ・監査証跡の実装状況が未確認
