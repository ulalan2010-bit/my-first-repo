# Issue修正(reservation_app)

レビュー指摘・テスト失敗を修正する工程。修正は理解を伴う作業なのでサブエージェントに丸投げせず、メインセッションが直接行う。共通規約は `issue-flow` スキルを参照。

## 手順

1. `docs/issues/<番号>/review.md` の最新レビューと `docs/issues/<番号>/test-report.md` の最新結果を読む。
2. 対応する指摘・失敗を一覧化する(重大度順、Critical/Highから)。
3. 1件ずつ:
   - 原因を確認する(推測で直さない。該当コードを実際に読む)。
   - `design.md` の方針を変える必要がある修正であれば、design.mdも更新すべきかユーザーに確認する(設計そのものが誤っていた場合)。
   - タスクに無関係な範囲までリファクタしない。
4. 修正をコミットする(コミットメッセージに `#<番号>` と、対応した指摘の要約を含める)。
5. 修正が一通り終わったら、`issue-review` と `issue-test` を再実行して収束したか確認する(呼び出し元が`issue-flow`ならオーケストレーターがこれを行う)。
6. 収束しない場合(同じ指摘が繰り返される、新しい問題が出る)は、設計そのものを見直すべきかユーザーに相談する。無限にこの工程だけを繰り返さない。

## ラベル

修正が完了し次のレビュー/テストに回す準備ができたら、`stage:needs-fix` → `stage:review` または `stage:testing` への付け替えをユーザーに確認する。

## 完了条件

- Critical/High指摘が解消されている(Medium/Lowは対応方針が明確になっている)
- 修正がコミットされている
- 再レビュー/再テストの必要性がユーザーと合意できている
